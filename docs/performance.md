# Performance notes

Measurements are real runs against PostgreSQL 16 on the build machine, not estimates. Sections are per area.

## Reports and dashboard (`apps/reports`)

### Method

- Scratch databases (never the dev or test DB), generated by a throwaway script that is not in the repo: 5 branches in three time zones
  (UTC, Asia/Tokyo, America/New_York), 120 products in 8 categories, 3,000 customers, 15 coupons and orders spread randomly over the last
  400 days (80% COMPLETED, 6% CANCELLED, the rest in progress; mixed payment states, 15% discounted, 20% delivery, 5% partly refunded).
  - **20k dataset**: 20,000 orders, 43,457 order items, 15,461 payments, 30,000 stock movements. About 1,400 orders fall in any 30-day window.
  - **200k dataset**: 10x the above (200,000 orders / 433,283 items / 154,450 payments), used only to see how the same queries scale.
- Queries were captured from the real endpoint (`GET /api/v1/admin/dashboard/`, uncached) and re-run under `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)`
  after `ANALYZE`. All data fits in `shared_buffers` (every plan shows `shared hit` only), so these are warm-cache numbers; cold-cache
  numbers will be worse. Wall-clock figures are in-process through the Django test client (session auth, serializers, JSON), median of
  4 warm runs after one warm-up. Timings are noisy (roughly +/-20% run to run).

### Headline numbers

| Scenario (20k orders) | Queries | Sum of SQL execution | Endpoint, uncached | Endpoint, cache hit |
|---|---|---|---|---|
| All branches (3 zones), 30 days | 17 (3 are auth/session) | 32 ms | about 82 ms | about 5 ms |
| All branches (3 zones), 400 days | 17 | 263 ms | about 298 ms | about 8 ms |
| One branch (UTC), 30 days | 17 | 29 ms | about 85 ms | about 6 ms |
| One branch (Tokyo), 400 days | 17 | 42 ms | about 101 ms | about 6 ms |

At 200k orders the summed SQL time (EXPLAIN ANALYZE, includes its own overhead) is about 300 ms for a 30-day window (one branch about 270 ms) and
about 1.3 s for the 400-day maximum. The dashboard payload is cached for 60 s per branch-scope and parameter set, so these costs are paid at most
once a minute per distinct filter. Cache hits cost one session lookup, the user, the staff profile and the branch lookup (4 queries).

What dominates: the two aggregations over `orders_orderitem` joined to `orders_order` (categories and products; both are needed by the payload),
then the order KPI aggregate (run twice, current and previous period) and the per-day series. Everything is a single grouped query per figure;
no row-per-order work happens in Python.

Reading the plans:

- The `placed_at` window is sargable: a 30-day window uses a bitmap scan on `orders_order_placed_at_*` (about 1,400 of 20,000 rows),
  while the 400-day window correctly falls back to a sequential scan because it matches essentially the whole table.
- The planner never uses the composite `(branch, status, -placed_at)` index for these queries: the counting rule is `status <> 'CANCELLED' AND
  (payment_status IN (...) OR (payment_method = 'cash' AND status = 'COMPLETED'))`, which is not a prefix match for it. Status and payment filters
  are applied as heap filters (for example 250 of 1,406 rows removed in the series plan), which is cheap at this size.
- With several time zones in scope the plan carries a `Join Filter` on `timezone(branch.timezone, placed_at)::date`. It removes only the handful of
  rows near the window edges (22-27 rows in the 30-day plans, 9-12 in the 400-day plans) and adds a join to the 5-row branch table. With a single zone
  (any single branch, or branches that share one zone) the window is an exact `placed_at` range and the join filter disappears.
- Item aggregations nested-loop into `orders_orderitem_order_id_*` (2 items per order, 50,161 buffers hit for the 16,633 orders of the 400-day
  plan). For one-branch 30-day windows the planner instead hash-joins a sequential scan of `orders_orderitem` (43k rows, about 2.6 ms); both are
  fine at this size.
- Attention counts scan the whole `orders_order` table by design (they describe "right now", not the date range): about 6 ms at 20k and 30-50 ms at 200k.
  Splitting them into three `WHERE`-led counts was tried and was about 30% faster at 200k (27 vs 39 ms wall-clock) for two extra round trips, so it was not
  adopted; the 60 s cache is the mitigation.

### Index recommendation: none for now

Candidate indexes on `orders_order` were created one at a time in the scratch databases and the full set of captured dashboard queries re-timed
(sum of median SQL execution per scenario, 9 runs per query):

| Orders | Scenario | Existing indexes | + `(branch_id, placed_at)` | + that and `(payment_status, placed_at)` | + `(payment_status, placed_at)` only |
|---|---|---|---|---|---|
| 20k | all branches, 30 d | 30.0 ms | 28.5 | 29.4 | 36.5 |
| 20k | one branch, 30 d | 24.9 | 24.4 | 25.2 | 29.9 |
| 20k | all branches, 400 d | 317.9 | 330.5 | 269.3 | 258.8 |
| 200k | all branches, 30 d | 326.8 | 313.1 | 307.7 | 273.2 |
| 200k | one branch, 30 d | 269.8 | 262.7 | 198.6 | 162.4 |
| 200k | all branches, 400 d | 1285 | 1352 | 1234 | 1222 |

None of this is a clear win. At 20k orders every variant is within noise (or slower). At 200k the `(payment_status, placed_at)` variants look better
for the one-branch 30-day case (270 -> 162 ms) but not for the others, and the cache already absorbs repeated loads. This was a single measurement
series, so treat it as inconclusive rather than as proof. **I am not recommending any new index**; revisit if the dashboard is regularly requested
with many distinct filters on a table well above 200k orders, in which case `(payment_status, placed_at)` is the first candidate to re-measure.
The counting rule contains an OR on `payment_method`/`status`, so an index cannot serve it alone; the useful part is only the `placed_at` range.

Changes made because of these measurements: the dashboard computes the top products with one grouped query (it used two) and skips the
distinct-order-count totals query for categories, removing two of the four item-level aggregations (summed SQL time for the 400-day, all-branch case at 20k went from 460 ms to 263 ms).

### Caching and limits

- `GET /admin/dashboard/` is cached for 60 s in the Django cache (Redis in production) under the namespace `reports`, keyed by the *effective*
  branch scope (`all` or the sorted branch ids), the selected branch, dates, granularity and whether the viewer has `customers.view`.
  Redis outage degrades to uncached responses (`IGNORE_EXCEPTIONS`), never a 500. Reports (`/admin/reports/*`) are not cached.
- Date ranges are limited to 400 days and every report is bounded (grouped by SKU/category/branch/coupon, or paginated for row-level lists), so
  worst-case work is a function of the date range and catalogue size, not of the number of customers.
- CSV exports stream (`StreamingHttpResponse`); row-level lists (refunds, stock) use `.iterator()` server-side cursors, grouped reports are
  bounded by catalogue size. Exports are not rate-limited by this app; add a throttle scope in settings if abuse is a concern.

## Reports: counting rule and edge cases (summary, authoritative text at `GET /admin/reports/definitions/`)

- An order is a sale when `status != CANCELLED` and (`payment_status` in PAID / PARTIALLY_REFUNDED / REFUNDED, or `payment_method = cash` and `status = COMPLETED`).
- A **cancelled order that was paid** is not a sale; it appears in the "refund needed" list (`attention.refund_needed`, refunds report) until `refunded_total = total`.
- AUTHORIZED-only (not captured), unpaid, failed and cash-not-yet-completed orders are not sales. They still count in "orders placed" and in the status breakdown.
- Refunds are attributed to the order's placed date (not the refund date) and are only netted for counted orders; a refund on a cancelled order shows in the refunds list with `counted_in_sales = false`.
- Days are branch-local. With several time zones in scope each order is bucketed in its own branch's zone.
- Item-level reports (products, categories) use the order-item snapshots; their `net` is `line_total - discount_amount` and does not allocate refunds, so `net(products) = net_sales + refunds`.
- Stock KPIs are snapshots of now (no previous-period comparison).
